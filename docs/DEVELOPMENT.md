# Working across the InteliBoy repositories

A proposal. Four repositories today, eleven if `subprojects.md`
happens, and no CI in any of them. This is about keeping them consistent
without slowing anything down, and about making the loop from *changed a line*
to *knew whether it worked* short enough that nobody skips it.

This file belongs in the superproject described in §4. It is here at the
workspace root until that exists.

---

## 1. Where this is heading

| repo | language | build | what breaks if it changes |
|---|---|---|---|
| `lfs` | shell + make | hours, docker, root | the image, and every package in it |
| `avatari` | C11 | seconds | every process that draws — cogiti, every feed, every service |
| `reflexi` | C11 + python | seconds | cogiti's ABI, and every intent |
| `cogiti` | python | seconds | everything it orchestrates |
| `audi` | C++/python | minutes | cogiti's turn edges |
| `agenti` | python | seconds | cogiti's job pipeline |
| `memori` | python | seconds | cogiti's prompts |
| `custodi` | python | seconds | services and jobs |
| `vidi` | C++/python | minutes | identity, and Stage 12's presence |
| service SDK | python | seconds | every service ever generated |
| `probi` | python | seconds | every eval number in every repo |

Three properties of that table decide the whole answer. The build times differ
by four orders of magnitude, so one CI pipeline over everything is wrong. The
`lfs` repo is enormous and root-privileged, so a monorepo is wrong. And every
row's "what breaks" column names *another repo*, so independent repos with no
shared discipline is also wrong.

## 2. The seams, which is where the breakage will be

Nothing will break in the middle of a repository. It will break at these
eleven places, and each one deserves a named owner and an automated check.

| seam | between | how it breaks |
|---|---|---|
| scene + speak protocol | avatari ↔ cogiti, feeds, services | a field is renamed; the renderer warns to a log nobody reads |
| `hello` capabilities | avatari ↔ everyone | cogiti uses a kind this renderer does not have |
| reflexi ABI | reflexi ↔ cogiti | a struct grows; ctypes reads garbage silently |
| blob format + normalizer | reflexi build ↔ reflexi runtime | **already solved** — see §3 |
| decision contract | reflexi ↔ cogiti | a new verdict or tier cogiti does not handle |
| intent registry ↔ command table | reflexi ↔ cogiti | an intent id or slot name is renamed; the command silently escalates |
| audi / agenti / vidi protocols | those ↔ cogiti | not written yet, which is why this is the moment |
| service manifest | SDK ↔ cogiti ↔ generated services | a field an agent wrote last month no longer parses |
| config file ↔ code | within avatari, soon cogiti | **already solved** — `make check-config` |
| package closure | lfs ↔ every binary | a new dlopen dependency ldd cannot see. **Already solved** — `RUNTIME_REQUIRES` |
| source hand-off | avatari, cogiti → lfs `sources/` | a tarball copied by hand, checksummed by hand |

That last row is worth reading twice. `x-make-avatari.sh:26` says the tarballs
are produced "by `make avatari-sources`, which runs avatari's own `make dist`
and copies the tarballs here". **That target does not exist in `lfs/Makefile`.**
The step is a manual `make dist`, a manual copy into `sources/`, and a manual
edit of `sources/local.md5sums`. It works because one person does it, remembers
it, and there is one program. With three programs and a dozen packages it is
the first thing that will ship a stale binary into an image and cost an
afternoon to find.

## 3. You have already solved this three times. Name the pattern

The best practice in this codebase was invented independently in all three
repos, and it does not have a name yet:

> **Wherever one fact is stated in two places, there is an automated check that
> the two agree, and it runs in under a second.**

- **reflexi**: the normalizer tables are compiled into `src/gen_*.h` rather than
  retyped, a hash over them is stamped into the blob and verified at load
  (`REFLEXI_E_CONTRACT`), and `tests/fixtures/tokens.txt` is generated by
  Python and asserted by C. Three layers of the same idea, on the seam that
  fails silently.
- **avatari**: `make check-config` diffs `etc/avatari.conf` against what
  `--print-config` reports, because "the shipped conf and the table in
  `src/config.c` are two statements of the same defaults, and they will drift".
- **lfs**: `make check` resolves every program against the rootfs, `make
  deps-check` verifies each distro's package list against the derived graph,
  and `RUNTIME_REQUIRES` records the dlopen edges ldd cannot see.

Everything in the rest of this document is that rule applied to the seams in
§2 that do not have it yet. That framing matters more than any specific tool:
when a new seam appears, the question is not "should we test this" but "what
are the two statements, and what compares them".

## 4. The superproject

Add one repository, `inteliboy`, that owns nothing and integrates everything.

```
inteliboy/
  README.md            what the appliance is; the map of the other repos
  HOUSE-RULES.md       the conventions every repo's CLAUDE.md includes (§11)
  versions.toml        the known-good set: one commit sha per repo
  Makefile             the integration verbs (§10)
  contracts/           the drift check, not the specs (§5)
  integration/         scripted sessions that run the real stack (§7, level 2)
  target/              qemu, deploy and smoke tests (§8)
```

**Not a monorepo.** `lfs` alone carries a 3.4 GB toolchain tarball and needs
root and docker; `avatari` builds in seconds. Merging them means every C change
sits behind the wrong CI, and it throws away three clean histories.

**Submodules or a `versions.toml` — pick one and do not mix.** Submodules give
you `git clone --recursive` and an atomic "this set is good" commit, at the
cost of a UX everyone complains about. A plain `versions.toml` plus a `make
sync` that checks out each sha is simpler, works with agent sessions that get
confused by submodule state, and is what I would choose here.

The superproject's only real product is that file. **`versions.toml` is the
known-good set: the last combination of commits proven to boot together.**
Images are built only from a known-good set. A rollback is a previous one. A
release is a tag on it. Everything else in the repo exists to promote a
candidate into it.

## 5. Contracts: one owner, a conformance kit, vendored fixtures

For each protocol in §2, exactly one repo is the owner, and the owner publishes
a **conformance kit** as part of `make dist`:

```
contract/
  scene-protocol.schema.json     machine-readable, versioned
  fixtures/valid/*.jsonl         every message shape, one per line
  fixtures/invalid/*.jsonl       with the reason it must be rejected
  VERSION                        one integer, plus a capability list
```

Consumers vendor that directory and run it in their own test suite. This is
exactly reflexi's cross-language fixture pattern (`tests/fixtures/tokens.txt`
generated from Python, asserted in C), generalised — which is the point: it is
a practice this project already trusts, not a new one to adopt.

| protocol | owner | consumers |
|---|---|---|
| scene + speak | avatari | cogiti, service SDK, every feed |
| decision contract + ABI | reflexi | cogiti |
| audi | audi | cogiti |
| agenti | cogiti (it defines the job contract) | agenti |
| vidi | vidi | cogiti |
| service manifest | cogiti | SDK, generated services |

**Rules for changing one:**

- Additive is free. A new optional field, a new op, a new kind: no version
  bump, and old consumers keep working because unknown fields are ignored and
  unknown kinds degrade — which avatari already guarantees.
- Removing or changing the meaning of anything bumps the integer and is a
  superproject commit that moves every consumer in the same known-good set.
- **The runtime check already exists and should be used**: avatari's `hello`
  replies with its `kinds`, `regions`, `lifetimes` and `ops`. cogiti asserts at
  startup that everything its command table and presentation templates need is
  in that list, and fails loudly naming the missing one. A device that renders
  a `fallback` instead of a chart, silently, forever, is the failure this
  prevents.
- One CI job in the superproject — **contract drift** — checks that every
  vendored copy matches the owner's current version at the known-good set. It
  is thirty lines and it is the single highest-value piece of automation on
  this list.

## 6. Every protocol owner ships a fake of itself

This is the biggest lever on the implement-to-test cycle, and it is nearly
free because it falls out of the conformance kit.

**Nothing should ever need another real component in order to be tested.**

avatari already gets half of this right: `tools/feed.sh`, `demo-scene.py` and
`brain-sim.py` are a fake *brain*, so the renderer is developed with no AI
stack present. What is missing is the mirror image — a fake *renderer* — and
cogiti cannot be tested without one.

| owner | ships today | owes |
|---|---|---|
| avatari | a fake brain (`brain-sim.py`) | **a fake renderer**: speaks the protocol, records ops, asserts, no GPU |
| reflexi | `reflexi-cli`, which is already this | — |
| audi | — | `--replay file.wav`, and a fake that emits scripted transcripts with realistic partial timing |
| agenti | — | `--driver mock` with scripted outputs |
| vidi | — | a fake emitting scripted identity and QR events |
| cogiti | — | a fake service, for testing the supervisor |

`probi` is where the fakes are composed into a whole device. But each fake
belongs to its protocol's owner, not to `probi`, because the owner is the only
one who will remember to update it.

## 7. The test ladder

Five levels, each with a time budget. The budget is the design constraint: a
level that stops fitting in its budget gets split, not tolerated.

| level | what | budget | when it runs |
|---|---|---|---|
| **L0** | compile, unit tests, the drift checks of §3 | **5 s** | on save; pre-commit hook |
| **L1** | full per-repo suite, contract conformance against vendored fixtures, `make eval` | **60 s** | on push; CI per repo |
| **L2** | integration on the workstation: real cogiti, real avatari (desktop backend), fake audi and agenti, scripted sessions | **3 min** | CI on the superproject; locally before a known-good bump |
| **L3** | on-target smoke: boot the image in qemu, assert first frame, run a scripted session over the deploy channel | **10 min** | nightly, and before promoting a known-good set |
| **L4** | full package build and image | hours | on release, and when `packages.list` changes |

The two that do not exist yet and matter most are L2 and L3. L2 is `probi`
plus the fakes from §6 and is worth building during cogiti Stage 0, exactly as
`docs/subprojects.md` argues. L3 is §8.

## 8. Getting onto the target quickly

Today, proving a change on the appliance means: `make dist` in avatari, copy
the tarball into `lfs/sources/`, edit `local.md5sums`, rebuild the package,
`make distro`, `make image`, `make qemu`. Most of it is manual and the last two
write three gigabytes.

Three changes, in order of payoff:

**a. `make push` — write into `rootfs/` and reimage, one command.** The
machinery exists: `make install-package PACKAGE=...` installs into `rootfs/`,
and `make image` turns `rootfs/` into the image. Chaining them behind one verb,
with the source hand-off automated (below), turns the loop into one command and
a couple of minutes.

**b. Reach the running guest.** `scripts/image/qemu.sh` uses `-netdev user`
with no `hostfwd`, so nothing on the host can talk to the booted appliance —
which means every change costs a reboot, and no test can drive the device while
it runs. Two ways, and I would do the first:

- Add `hostfwd=tcp::2222-:22` and put a small ssh daemon in the *development*
  distro only (dropbear is a few hundred kilobytes; openssh is heavier and
  brings its own dependencies). Deploy becomes `scp`, and L3 becomes a script.
  The appliance distro ships without it, so this costs the product nothing.
- Or forward the cogiti and avatari sockets over a virtio-serial channel and
  drive them from the host. Smaller, no network, no new package — but a new
  mechanism to write and maintain.

**c. A boot smoke test that asserts something.** Boot in qemu, wait for the
renderer's first frame, run three scripted utterances through cogiti, capture
the framebuffer, assert the scene ops. Ten minutes, unattended, and it is the
only thing that will catch a Mesa or KMS regression before the hardware does.

**And fix the source hand-off.** Add the `make avatari-sources` target that
`x-make-avatari.sh` already documents, generalise it to `make sources
PROJECT=...` for cogiti and the rest, and have it run the project's `make
dist`, copy the tarballs, and rewrite `local.md5sums` itself. It is twenty
lines and it removes the manual step most likely to ship a stale binary.

## 9. CI

None of the repos has any. GitHub Actions, and keep it proportionate:

- **Per repo, on push:** L0 and L1. For `avatari` that is a `PLATFORM=desktop`
  build plus a `PLATFORM=kms` *compile* (the kms build must never be left
  unbuilt for more than a milestone, and CI is how that promise is kept). For
  `reflexi`, `make test && make eval`. For the Python repos, `mypy --strict`,
  `pytest`, and the conformance kit.
- **Superproject, on any version bump and nightly:** contract drift, L2, then
  L3 on a self-hosted runner (the workstation), then promote the set if
  everything passes.
- **Never in CI:** the full LFS package build. Hours, root, docker-in-docker.
  It stays a local target and a release step.

**Automate the eval-delta habit.** Every repo's CLAUDE.md asks for the eval
numbers before and after, in the commit message. Make `make eval` emit JSON,
have CI compare against the base branch, and print the delta into the job
summary — with a gate that fails on a regression the author did not
acknowledge. A discipline that depends on remembering will not survive eleven
repositories and several parallel sessions.

## 10. One vocabulary

Every repo, the same verbs, so muscle memory and agent sessions transfer:

| verb | means |
|---|---|
| `make` | build the thing |
| `make test` | L0 + L1 for this repo |
| `make eval` | the measured numbers, and print them |
| `make run` | run it locally against fakes |
| `make fake` | run *this repo's* fake of itself |
| `make contract` | regenerate and verify the conformance kit |
| `make dist` | the source tarball lfs consumes |
| `make check` | the drift checks of §3 |

avatari and reflexi already have most of these. The two new ones are `fake`
and `contract`, and adding them to the existing two repos is an hour each.

## 11. House rules, stated once

Reading the three CLAUDE.md files together, the same conventions appear in all
of them, phrased differently each time:

- one terminal command at a time;
- prefer data over code, and ask whether a feature could be a row;
- eval before and after, both numbers in the commit message;
- fail loudly at init, degrade gracefully at runtime;
- state the LFS build cost when proposing a dependency;
- no new dependency, framing, or protocol without discussing it first;
- push back on scope creep.

Put them in `inteliboy/HOUSE-RULES.md`, have each repo's CLAUDE.md open with a
one-line include, and add a drift check that the included copy matches. That
is §3 applied to prose, and it costs nothing.

## 11b. Versions: every change gets one

**Semver, and the major stays 0 until the appliance is a production release.**
0.y.z is semver's own name for "anything may change", which is exactly true
here; 1.0.0 is a promise about compatibility that nothing is ready to make.

- **patch** — fixes, and nothing a user could ask for that they could not
  ask for before.
- **minor** — anything new: an intent, a provider, a port filled, a setting.
- **major** — not until production. `tools/release.sh` refuses the word, so
  reaching 1.0.0 is an edit to that script and cannot be a typo at a prompt.

Every repository carries its own version as an **unprefixed git tag** —
`0.2.0`, never `v0.2.0` — and the appliance carries one for the image as a
whole. A component's tag says what that component is; InteliBoy's says what
was flashed. They move independently and are not expected to match.

For the appliance, use the tool rather than editing anything:

    tools/release.sh minor      # or patch
    tools/release.sh --check    # verify, change nothing

It exists because `distro.conf` states the number **twice** — `VERSION`, and
again inside `PRETTY_NAME` — and lfs *reads* that file rather than sourcing
it, deliberately, so one field cannot refer to another. Two hand-maintained
copies of a number is a drift waiting to happen; `--check` fails if they
disagree with each other or with the latest tag, so an image can never claim
a version nobody released.

For a component, the tag is the whole ceremony:

    git tag -a 0.2.0 -m "cogiti 0.2.0" && git push --tags

**A version that never moves is worse than no version.** The device reported
`InteliBoy 0.0.0` across every image ever built, including two that differed
by a working voice — so the one question a running device can always answer,
*what are you*, was answered identically by every one of them.

## 12. Operating it from a Claude session

The structure decided in §4 — a main repo containing every component, with lfs
outside it as a tool — makes one **mediator session** rooted at `inteliboy/`
possible: it can read every component, edit across them, and see both sides of
a seam in one place.

It should not use that power evenly. There is a sharp line, and most of the
risk is on one side of it.

### Delegate reading freely. Delegate writing reluctantly.

**Reading fans out perfectly.** "What would adding a `chart` kind touch in
this repo?" asked of five repos at once is five independent, idempotent,
conflict-free questions, and each answer is two paragraphs of conclusion drawn
from thousands of lines the mediator never has to hold. This is what subagents
are actually good at, and it is where the leverage is.

**Writing does not.** A write is stateful, order-dependent, needs verification,
and produces a git working tree that another agent can walk into. Every risk in
the register below is a writing risk.

The practical rule: **survey with agents, decide alone, and write by hand
unless the change is large and mechanical.** Six agents making three-line edits
in six repos is slower, costlier and less reliable than doing it yourself.

### The five phases

```
1. survey     N read-only agents, one per repo, one question each
              → the mediator keeps conclusions, not file contents

2. design     the mediator alone. Writes changes/<id>/brief.md.
              → stops. A person approves the brief before any code.

3. implement  small change  → the mediator, repo by repo, in landing order
              large change  → one worker agent per repo, brief as input

4. verify     the mediator runs each repo's `make test` itself.
              A report is a claim; a test run is evidence.

5. integrate  bump versions.lock, run L2, commit the brief.
              Never delegated.
```

Phase 2 stopping for a person is not ceremony. It is the only point where the
cost of being wrong is one paragraph rather than five repositories.

### What a worker agent is told, and what it may never do

The brief section is its whole input, and it must be complete, because **a
subagent cannot ask you anything.** Given an ambiguity it will resolve it
plausibly and silently, and plausible-and-wrong is the expensive failure. So
the instruction is explicit: *on anything the brief does not settle, stop and
report the question rather than choosing.*

Never, for a worker agent:

- touch a repo other than the one its section names;
- touch `versions.lock`, or any contract its repo does not own;
- touch `lfs` — the orchestrator edits it when a brief says to, and the user
  commits it. For a worker agent it is a proposal, never a patch made in
  passing;
- commit to `main`, or push anything;
- decide anything the brief left open.

Work lands on a branch named for the change id in each repo, so unwinding a bad
change is deleting branches rather than reverting across five histories.

### The risk register

| risk | why it bites here | what removes it |
|---|---|---|
| **the agent's context dies with it** | it learned how `scene.c` composites layers; you get three sentences and the rest is gone | require findings written into the brief, not just reported |
| **two agents in one repo** | same clone, same files, silent clobbering | one agent per repo, ever. Fan out *across* repos, never within one |
| **a report is a claim** | "done, tests pass" from an agent that ran nothing | the mediator runs `make test` itself and reads the output |
| **it cannot ask** | resolves ambiguity plausibly and wrongly, and says nothing | complete briefs; "stop and report the question" as a standing instruction |
| **fixing from the wrong side of a seam** | a cogiti agent adds a field to avatari to unblock itself | the brief names one repo; owner-first landing order (§5) |
| **lfs gets patched in passing** | the tool acquires a distro of ours, a file of ours, or a fix nobody designed | no agent writes there; the orchestrator edits only from a brief and never commits — the user does |
| **five agents, five vocabularies** | the same error category named five ways in five repos | the brief carries the shared names explicitly; anything unnamed is a question |
| **N dirty working trees** | a change abandoned halfway leaves every repo half-edited | branch per change id; nothing on main; nothing pushed |
| **the mediator fills up anyway** | it still holds the plan, N reports and the integration reasoning | the brief on disk is the durable state — that is its real purpose, not tidiness |
| **delegation costs more than it saves** | six agents for a six-line change | delegate reads; hand-do small writes |
| **worktree isolation may not do what you expect** | the components are nested repos inside the main one; which repo a worktree is taken of is not obvious | verify the behaviour on a throwaway change before relying on it |

### What is never delegated

- the seam decision, and which repo owns it;
- any contract version bump;
- `versions.lock`;
- the first implementation of a new protocol — the shape matters more than the
  code, and shape is exactly what a fresh context gets wrong;
- anything in cogiti's consent, secret or egress policy. `../../cogiti/docs/security.md`
  says an agent proposes and cogiti decides. The same rule applies one level up:
  an agent proposes changes to that policy, and a person decides.

### When components disagree

A standing agent per component — spawned once, re-messaged through a change,
keeping its context — is worth having. But it is worth being exact about what
it is for, because the obvious framing is the wrong one.

**Two agents asked to reach agreement will reach it.** There is no cost to
agreeing, no adversarial pressure, and no shared stake in being right. What
looks like a negotiation converging is usually two contexts being polite. The
failure mode is violent agreement on a bad design, arrived at quickly and
reported confidently.

So do not ask them to agree. **Ask them to object.**

Each of these repositories has a written *Hard boundaries* section — invariants
its author already decided are not negotiable. That is exactly the mandate a
standing component agent should carry:

> You represent `avatari`. Its hard boundaries are below, verbatim. Your job
> is to say what this proposal costs us and what we would refuse, and to
> explain why in terms of those boundaries. If the orchestrator tells you a
> decision has been made that violates one of them, refuse and say which.
> Do not agree in order to be helpful.

That standing instruction lives in the agent's definition, not in a single
request, so it outlives however the orchestrator happens to frame any one
round. An agent told "we've decided on X, implement it" will otherwise
implement X, invariant or not.

The four kinds of conflict, and which of them this actually helps with:

| conflict | example | resolved by |
|---|---|---|
| **file** | two agents editing `scene.c` | partitioning — one agent per repo. Never negotiation |
| **ordering** | cogiti cannot land before avatari | the owner-first rule (§5). Deterministic; no agents needed |
| **vocabulary** | five repos naming one error category five ways | the brief carrying the names. Stated, not negotiated |
| **design at a seam** | the brain wants coordinates; the renderer owns layout | **this one**, and only this one |

Three of the four are structural and already handled. Building a negotiation
apparatus for all four is overhead on the ninety percent of changes that have
no conflict at all — a contract gets extended and three consumers follow.

### The round protocol, and its cap

```
R0  the orchestrator states the goal and the seam to each affected agent
R1  each returns: feasible? what does it cost us? what would we refuse?
                 what would we prefer instead?
    → the orchestrator writes the positions into the brief, in their words
R2  the orchestrator proposes one design; each returns accept, or object
    with a reason
    → any objection that still stands goes to the human. There is no R3.
```

Two rounds, then you. The cap is the point: rounds are cheap for the agents
and expensive for the orchestrator, which must hold every position, and an
unbounded exchange spends the orchestrator's context on transcript instead of
on the design.

Note what the orchestrator is doing here: relaying. There is no agent-to-agent
channel to assume — every message passes through it, and it is also the only
path to you. That is the same job you are doing today, moved inside the model.
It is tireless and holds more detail than you do; it does not hold your
judgement about which design is actually right. Which is why R2 ends at a
person rather than at a consensus.

### Risks the standing-agent model adds

| risk | why | what removes it |
|---|---|---|
| **convergence theatre** | agreeing is free; disagreeing is not rewarded | mandate objection in the agent definition; require each to state what it would refuse |
| **sycophancy to the orchestrator** | "we've decided X" reads as authority | the boundaries are the agent's standing mandate, above any single request |
| **stale context** | a long-lived agent's view of its files is from when it looked | treat a standing agent as holding *design* context, never *file* context. It re-reads before it writes |
| **the negotiation is invisible to you** | you get a summary of an exchange you did not watch | positions go into the brief in the agent's own words, not paraphrased |
| **nobody owns the outcome** | a design with five parents has none | the brief plus your approval. The orchestrator writes the decision; it does not discover it |

### Advising and implementing

The same standing agent may implement what it advised — its context is the
expensive part and throwing it away is wasteful. But it is the worst available
reviewer of its own proposal, so verification stays where §12 put it: the
orchestrator runs `make test` in that repo and reads the output. An agent's
assessment of its own work is not evidence.

### Sessions other than the mediator

Component work that is not part of a cross-repo change does not need the
mediator at all, and is better off without it. Open a session rooted **inside**
the component — `inteliboy/avatari/`, not `inteliboy/` — because the narrower
directory is what stops a well-meaning session from reaching across a seam and
creating the drift this whole scheme exists to prevent. Use worktrees rather
than switching branches under another session's feet.

Roles, then:

| | mediator | worker agent | component session |
|---|---|---|---|
| rooted at | `inteliboy/` | `inteliboy/<repo>/` | `inteliboy/<repo>/` |
| lives for | one change | one brief section | as long as you like |
| may write | briefs, contracts, docs, the lock | its repo, on a branch | its repo |
| decides | the seam, the shape, the order | nothing | implementation |
| can ask you | yes | **no** | yes |

## 13. The goal, and what stands between here and it

The goal is one session you speak to, which fans work out to the components in
parallel and verifies the result at the end.

**It is achievable, and the thing standing in the way is not the orchestration.
It is that only one of the four repositories can currently tell an agent it
broke something.**

### What already works

- One session as the only interface: yes, today.
- Parallel fan-out across components: yes, and safely — separate directories,
  separate git repositories, no shared files. Parallelism *across* repos is the
  easy case; it is parallelism *within* one that is unsafe, and the structure
  already rules that out.
- Front-loading the questions: yes. A subagent cannot ask you anything, so the
  orchestrator has to ask everything during design, before any code. That is a
  constraint but not an obstacle — it means the conversation is concentrated at
  the start rather than spread through the work.

### What does not, yet

Verification. Spelled out honestly:

| repo | what `make test` would actually prove today |
|---|---|
| `reflexi` | a real C suite, cross-language fixtures, and a scored `make eval`. **This one works** |
| `lfs` | structural checks — `make check` resolves every binary, `deps-check`, `deps-verify`, the shared-file policy gate. Real, but nothing that says the image boots |
| `avatari` | that it compiles, and `check-config`. No behavioural suite: a change to `scene.c` has nothing that fails |
| `cogiti` | nothing. There is no code yet |

An orchestrator that fans out five changes and then "verifies" against that
will report five successes. It will be right about one of them and unable to
tell you which.

**So the ceiling on autonomy here is set by the test suite, not by the model.**
Everything in §5 through §9 — the conformance kits, the fakes, `probi`, the
per-repo `make test` — reads like tidiness and is not. It is the precondition
for the thing you actually want.

### One correction to the shape

Not one session forever — **one session per change.** The orchestrator holds
the plan, N reports, the verification output and the integration reasoning, and
on a large change it will run out of room. That is fine and expected: the brief
on disk is the durable state, so a fresh session reads
`changes/<id>/brief.md` and continues. Restartability is the reason briefs are
files, not the tidiness.

And "speak only once" settles in practice at: **you are asked everything at the
start, and asked to approve at the decision points.** Three approvals across a
change instead of forty relayed messages is the win — and the decision points
are the ones §12 lists as never delegated. A seam design, a contract bump, and
a security boundary are approvals you want, not overhead to remove.

### The order that gets there

Reordered around this goal, which changes the priorities: CI matters less than
it looked, because the orchestrator runs the gate locally itself, and the
target-hardware work matters less than it looked, because most changes never
touch the image.

1. **`make test` that means something, per repo.** The gate the orchestrator
   runs. avatari needs a behavioural suite before anything else here is
   trustworthy, and cogiti needs one from its first commit rather than later.
2. **A fake renderer in avatari** (`tools/fake-avatari.py`): speaks the scene
   protocol, records ops, asserts. It is simultaneously avatari's missing
   protocol test and the only way cogiti is testable at all. *Half a day, and
   it serves two of the four repos.*
3. **`probi` and L2** — the scripted-session harness. This is what turns
   "verify at the end" from a per-repo claim into one command that exercises
   the seams. cogiti Stage 0, as `subprojects.md` argues.
4. **Conformance kits**, starting with avatari's scene protocol. What makes a
   contract violation fail loudly in a consumer's own suite instead of at
   runtime on the device.
5. **The main repo, `versions.lock`, and the contract-drift job.** The
   orchestrator's integration step needs somewhere to land.
6. **`make sources PROJECT=...` in lfs** — removes the manual copy-and-checksum
   step, which is the one part of the pipeline an agent cannot be trusted with
   while it is manual. *An hour.*
7. **Per-repo CI.** Now a safety net under the orchestrator rather than the
   primary gate.
8. **`hostfwd` and the boot smoke test.** The last mile, and only needed for
   changes that reach the image.

Items 1 to 3 are the ones that convert the goal from "possible in principle"
to "trustworthy in practice". Nothing above them is worth doing first.
